## 2026-09-21 — Date/time picker: second bug report, redesigned as two controls

User reported the same "expanding infinitely" popover symptom from 2026-09-16 again, with fresh screenshots. Since a repeat report undermines the earlier "stale cache" conclusion, re-investigated more rigorously instead of repeating that diagnosis:

- Reproduced the component twice in isolated live browser tests — once via a mocked full-app boot attempt (abandoned after the mocked auth session proved unreliable to wire up against the real `App.jsx` routing/auth guard), and once via a minimal harness that imports every stylesheet the real app currently loads (`global.css`, `design-tokens.css`, `reports.css`, `v2-sf1-modal.css`, etc. — the full CSS surface as of today, not the smaller set that existed on 2026-09-16) and renders the exact same two-field grid layout `V2AssessmentEditorPage.jsx` uses.
- In both attempts, the picker rendered at its correct, compact size (~325×295px). The ballooning could not be reproduced outside the user's own browser session with either the old or the current CSS bundle.
- Given the inability to reproduce it twice now, root-caused this as a likely fragility rather than a proven, isolated defect: the original design rendered the calendar and the time list as two flex children inside one `.react-datepicker` row, in a popover with no `max-width`/`max-height` bound to the viewport. That combination is a known-fragile pattern for `react-datepicker` inline mode (the time list auto-scrolls to the selected time on open, which can interact badly with a not-yet-settled flex layout in edge-case timing).
- **Fix implemented regardless of exact trigger:** split `DateTimePicker` (`src/components/ui/date-time-picker.jsx`) into two independent trigger buttons and two independent popovers — one showing only the calendar (`inline`, no `showTimeSelect`), one showing only the time list (`inline showTimeSelect showTimeSelectOnly`). Each popover now renders exactly one widget, never two side by side, which removes the specific layout interaction under suspicion. The external component API (`value`, `onChange`, `minDateTime`, `id`, `disabled`, `placeholder`) is unchanged, so `V2AssessmentEditorPage.jsx` needed no changes at all.
- Verified live: picking a date closes the date popover and shows the date; the time button then enables and opens a compact time-only list (85×~247px, react-datepicker's own `.react-datepicker--time-only` modifier applied automatically); picking a time closes the time popover and combines both into the same `openAt`/`closeAt` string format the rest of the form already expects.
- **Status: Verified** for the isolated component in both old- and current-CSS contexts. Not yet watched inside the real authenticated app (the mocked-auth live-app test was abandoned as noted above, not a failure of the fix itself — the split component is a drop-in replacement with an identical contract).

**Same day, follow-up — user saw the bug a third time and asked to drop the custom design entirely.** A new screenshot showed the same combined-popover overlap symptom (the split-controls fix above had not yet reached whatever session/build the user was looking at). Given three reports of the same fragile pattern, replaced the entire custom `react-datepicker` + Radix `Popover` implementation with two plain native browser inputs (`<input type="date">` + `<input type="time">`) in `src/components/ui/date-time-picker.jsx`. This removes all custom calendar/popover rendering and positioning code — there is no longer any custom layout math that could balloon, since the calendar/time UI is now entirely OS/browser-native. Deleted the now-unused `src/styles/date-time-picker.css`. External contract (`value`/`onChange` as `YYYY-MM-DDTHH:mm`, `minDateTime`, `id`, `disabled`) is unchanged, so `V2AssessmentEditorPage.jsx` needed no edits. **Status: Verified** — value plumbing and the min-date/min-time constraint both confirmed live in an isolated browser test.

**Teacher Settings — logout confirmation.** Added a confirmation step before logging out (`src/pages/TeacherSettingsPage.jsx`): clicking "Logout" now opens a small dialog ("Are you sure you want to log out?" / Yes / No) instead of logging out immediately. Reused the existing `principal-teacher-confirmation` modal styling already established for the teacher-approval flow, so no new visual pattern was introduced. **Status: Verified** (lint + isolated render check). Note: the principal role has a separate, always-visible sidebar logout button (`AppLayout.jsx`) that still has no confirmation — flagged to the user, not changed without a separate request.

**Reports — learner name formatting and sorting.** User asked for every non-date-sorted name list to use Title Case and "Lastname, Firstname Middlename" ordering, matching the earlier roster fix. Audited every name field the Reports page renders against the actual backend DTOs (`V3ReportReferenceDataResponse`, `V3AssessmentResultsReportResponse`, `V3StudentPerformanceProfileResponse`, `V3ConsolidatedReportResponse`, `V3ItemAnalysisReportResponse`) rather than guessing from the UI alone:
- Every one of these only exposes a single combined `fullName` string — no discrete `lastName`/`firstName`/`middleName` fields exist for reports (unlike the class roster endpoint, which does have them). Splitting a combined Filipino full name into last/first/middle client-side is not reliable (compound surnames, multi-word given names), so doing that would mean guessing backend-owned data — against this project's explicit rule.
- Applied everything safely achievable now: Title-Case formatting on every `fullName` display (assessment-results table, student filter dropdown, teacher filter dropdown, student performance profile header), and alphabetical sorting of the assessment-results table rows (previously unsorted, backend row order) by the formatted name string.
- Sent the backend session a request to add discrete name fields to the four report DTOs above so the exact lastname-first reorder + true last-name sort (not just alphabetical-by-string) can be finished without guessing. **Status: partially verified** (Title Case + string-alphabetical sort confirmed via lint/read of the diff), reorder-to-lastname-first blocked on backend fields.

**Real bug found along the way: a Unicode title-case bug affecting any accented name, app-wide.** Backend flagged that "Añana" was rendering as "AÑAna" in the new Sync Activity table. Root cause: both `ReportsPage.jsx` and `ClassRecordsPage.jsx` have their own copy of `toTitleCase()` using `.replace(/\b\p{L}/gu, ...)`. JS's `\b` word-boundary is ASCII-only regardless of the `u` flag (the flag only makes `\p{L}` Unicode-aware, not `\b`), so any accented letter (ñ, é, ü, ø, ...) is misread as a boundary on both sides, capitalizing the letters immediately next to it too. Fixed in both files by matching an explicit, fully Unicode-aware boundary instead of `\b`: `(^|[^\p{L}\p{N}'])(\p{L})`. This was a real, previously-unnoticed bug affecting any Filipino name with an accented letter, not something specific to the new report — it would have shown up anywhere `toTitleCase` runs (rosters, other report tables) once a name like "Añana" appeared, which is why it's called out clearly here rather than folded silently into the Sync Activity entry above. **Status: Verified** — live-tested "HEART MILLAN AÑANA" → correctly renders "Heart Millan Añana" in both the teacher and assessment tables.
